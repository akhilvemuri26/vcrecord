Architecture and authorization

Use @supabase/supabase-js in the browser against https://hedvfgmuezfyhrrzcjok.supabase.co, project hedvfgmuezfyhrrzcjok, with the supplied publishable key. The publishable key is frontend configuration; never include a service-role, secret or Management API token in source or bundles. Keep Vite/GitHub Pages; no Next.js or SSR dependencies. Enable anonymous sign-in in this project. Reuse a persisted Supabase session, otherwise sign in anonymously when sharing is needed. Local practice must still work when auth or the network fails.

Anonymous sessions have distinct authenticated user IDs. A 32-byte cryptographically random invite secret grants team membership through an RPC. Use a URL fragment #team=<uuid>&invite=<64-hex-secret>, read and clear it with history.replaceState before other async work, then validate through the backend. Persist the pending invite locally until successful join so a failed connection is retryable. Do not log invite URLs or include them in screenshots/review artifacts. Store the successful invitation locally for Copy invite; the database stores only its SHA-256 hash. Anyone intentionally given that link can join the team. Project URL, publishable key, team UUID or a person's display name alone grants no team access.

Joining a new invite must not upload old private recordings automatically. Show the team and an explicit Share saved answers action for existing local items. New recordings made while joined are assigned to that team at capture start. Show Create team when no invite/session team exists, then Copy invite and Refresh/Retry sync. On failed invitation, retain existing team and local recordings. A newly created or joined team becomes active only after successful backend confirmation. Pending uploads retain their original team and owner; switching team must never retarget them.

Durable synchronization and migration

  1. Keep the local source first. Preserve the existing IndexedDB record shape and database/store so deployed recordings survive. Extend Answer with optional teamId, ownerUserId, sync state/error, monotonically increasing local revision, uploaded flag and deletion tombstone. Do not overwrite Blob/audio with metadata-only remote rows. Each local mutation that affects remote content marks dirty and increments revision atomically with the mutation.
  2. Upload immediately after committed local save. Freeze the chosen team and authenticated owner before upload; unconfigured/offline recordings remain local and can be shared later. Run upload independently of the Whisper queue. Save video once to the deterministic private path, then insert/update answer metadata. An uploaded object without metadata is safe and retryable. Treat only a verified existing-own-path conflict as upload already complete. Never label an answer Shared before metadata and video succeeded.
  3. One serialized sync loop. On startup, online, explicit Retry and successful local transcript mutation, drain dirty assigned records one at a time. No background timer storm. Network failure retains local content and error state; next trigger retries idempotently. After a successful send, mark synced only if the local revision still equals the sent revision; otherwise resend the current content. Stale upload completions cannot erase newer edits.
  4. Transcript updates follow the same queue. Whisper completion/error, manual save, and retry state changes persist locally, then enqueue sync. Keep the existing protection for edited transcripts and newer textarea drafts. Transcription stays local; do not upload Float32Array audio. Team peers see pending/transcribing/failed/ready states without blocking playback. Only devices with local source audio offer Retry transcription.
  5. Deletion is durable. For local/shared owned answers mark a tombstone and hide immediately, remove queued inference, then serialize remote row/object deletion and only finally delete the local record. Retry failures. An active sync must check the tombstone before marking success and must delete any just-created remote state. Late Whisper results cannot resurrect tombstones. Keep pending deletion metadata until both server operations succeed. Other members cannot delete or edit even through direct REST/storage calls.
  6. Merge library by answer UUID. Fetch team metadata on opening Answers, Refresh, successful sync and page focus, with bounded refresh while library is visible if desired. No Realtime dependency needed. Display local pending/unshared answers plus active-team remote answers, deduplicating by ID. Local dirty content wins until sync succeeds. Keep other-team local items out of the active team view or label them clearly; never upload them to the active team accidentally. Do not infer deletion merely from a failed remote list request.
  7. Playback and owner controls. Local source uses its Blob; remote source lazily downloads from the private bucket, checks selection is still current, and revokes replaced object URLs. Keep a metadata-only remote type separate from a fully local Answer. Hide/disable edit/delete/retry for other owners. Remote-only owned records can save editable transcript through a metadata update; they cannot retry Whisper without local audio.
  8. Legacy migration. Preserve every old recording unchanged and readable. Share saved answers is idempotent and assigns only unassigned selected/local records to the current team and current authenticated owner. Freeze person/name metadata; preserve existing question IDs and timestamps. Keep local saves after successful upload. Group people across devices by trimmed case-normalized display name; never use this label as ownership identity. Keep person_id as source metadata and auth.uid() as the edit/delete authority.

Anonymous identity is intentionally low friction. Clearing auth/site data loses that browser's ownership identity. Reopening the team invite restores read access and permits new answers, but does not regain editing authority over an old anonymous identity. Document this concise limitation in README/handoff, not in a replacement privacy paragraph. Do not implement accounts, recovery, invite rotation, billing, realtime, or a new server framework in this change.
