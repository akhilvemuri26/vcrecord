Implementation decisions

1. Preserve local recordings and merge safely

Extract a small testable library projection if helpful. Include every non-deleted local Answer with a Blob, independent of active team or authentication. Scope remote answers and remote-only edit overlays to memberships confirmed for the current session. Deduplicate by answer ID; local durable content or pending overlays win over fetched metadata, and tombstones suppress matching remote rows. Preserve original teamId, ownerId, object path, Blob, audio samples, and revisions. Do not reassign existing shared records merely to simplify the UI.

Render local results immediately when opening Answers, then refresh remote results; a slow or failed network must not delay access to on-device videos. Clear old-session remote caches on identity change and guard overlapping asynchronous refreshes so stale responses cannot replace the latest session or membership snapshot. A transient network failure may retain previously fetched answers for the same confirmed session, clearly marked as not refreshed.

2. Restore memberships and choose one destination

Add a sharing API calling the new accessible_teams() RPC described below. Restore authentication and discover accessible team IDs and their canonical destinations on startup and retry, even when vcrecord-team is absent. Validate stored preference and pending-invite shapes. Process a valid private invitation, then discover accessible teams again. Fetch and combine answers from confirmed accessible teams, with bounded requests and partial-failure reporting. Existing self-only team_members reads remain useful for diagnostics, but cannot by themselves reveal the linked legacy team's answers.

Use the existing canonical cofounder team as the destination for new shared recordings. The RPC supplies its UUID to authorized sessions. A canonical UUID is not a credential, but its private invite must never be bundled. Prefer the canonical destination returned for the current accessible group; otherwise retain a valid stored accessible team or a deterministic accessible fallback. Both old and canonical invite holders receive the same destination. New recordings receive a team only after access is confirmed. Offline practice still saves locally.

Keep the saved invitation separate from the active recording destination. A legacy token belongs to its original legacy team ID. When choosing the canonical destination, never combine the old token with the canonical ID. Preserve or migrate the existing {id, invite} pair as an independent invitation reference, and copy that original pair. Both valid old and canonical invite links work because the backend group supplies the shared access. A browser that discovers membership but has no invite secret must not show a fabricated Copy invite action.

Do not read teams directly: current grants forbid it. Do not implement an unauthenticated auto-join route, use a secret in source, or authorize by a selected name. A new browser with no existing membership needs the private invite. Explain this plainly in the disconnected state without claiming that selecting Akhil restores Akhil's old browser identity.

Keep explicit Share saved answers for genuinely unassigned local recordings, with a useful pending/local count; joining a link must not silently upload old local recordings. Never retarget records already assigned to any team. Only report connection success when membership discovery and relevant answer refresh succeed; upload failures and partial fetch failures remain visible and retryable.

3. Link exactly the two verified teams without moving recordings

Add a migration for a protected team_library_links table containing team_id (primary key and teams foreign key) and canonical_team_id (teams foreign key). Enable RLS and revoke all privileges from PUBLIC, anon, and authenticated; there is no client write or read policy. Root alone inserts the two verified mappings: canonical → canonical, legacy → canonical. Interpret the canonical value as a single group key, never recursively traverse aliases. No arbitrary teams, test teams, or inferred people are linked.

Replace is_team_member(p_team_id) so it requires a non-null auth.uid() and returns true for a direct membership or when the requested team's group key matches the group key of a team in which this user has a direct membership. This deliberately grants both old and canonical invitation holders access to the same recordings, including future valid invite joiners. Keep all existing answer/storage policies, exact owner checks, immutable metadata trigger, path constraints, private bucket, and invitation validation intact. Owner-only changes still require the original authenticated owner; display names grant no permissions.

Add accessible_teams(), a stable SECURITY DEFINER function with empty search_path, fully qualified references, explicit authenticated-only execute grant, and an auth.uid() check. Return only distinct accessible team_id and canonical_team_id pairs for the current user: direct unmapped memberships map to themselves, while direct membership in a linked group exposes all that group's mapped teams. Do not return invitation hashes, other users, or recordings. The direct self-membership policy remains unchanged. Use explicit revokes for default function execute permissions.

Root applies the generic migration and the precise two-team link after implementation review, with a private metadata/membership backup before mutation. Verify 188 + 35 = 223 answer rows remain, owners and object paths are unchanged, and object counts are unchanged. A new holder of either valid invite must be able to read both teams' answers and private videos; an unrelated authenticated browser must read neither. Keep both invite hashes and all old URLs valid. A rollback removes the two link rows and restores the prior function definitions; it never deletes recordings.

The root checked the official Supabase database function documentation and row-level security documentation for explicit grants, authenticated checks, and SECURITY DEFINER search-path constraints. Review the completed SQL against those requirements before applying it.
