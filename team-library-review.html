P2 — Opening Answers during connection can leave the status permanently Connecting

Location: src/main.ts:685–700, src/main.ts:739–749; triggered by the Answers navigation handler at src/main.ts:338–344.

After membership discovery starts the initialization fetch, opening Answers starts a second refreshRemote(). That increments remoteRefresh, so initialization's fetch returns false as superseded. Initialization then clears connecting without setting a final status. The second fetch can succeed and load every recording, but its caller only renders the library. The screen remains “Connecting to your cofounder library…” even though no connection operation remains active. This is a normal navigation path on a slow connection and violates the requested honest connection state.

Evidence: A focused Node VM probe transpiled and executed the actual three source functions (refreshRemote, syncAndRefresh, initializeTeam) with deferred fetches and stubbed browser dependencies. It started initialization, started the navigation refresh once initialization's two fetches were pending, resolved initialization, then resolved navigation. Result: {"status":"Connecting to your cofounder library…","connecting":false,"accessibleTeams":["legacy","canonical"]}. No app code was copied into a replacement implementation or edited for this probe.

Correction: Give a same-session connection refresh one authoritative completion path: coalesce overlapping same-generation refreshes, or let initialization await the replacement refresh and its result. Preserve the existing identity/generation checks and partial-fetch/upload-error reporting. Add a focused regression that navigates to Answers while initialization's answer fetch is deferred; after successful completion, recordings must be visible and status must report connected. Repeat with a replacement fetch failure and ensure a failure remains visible.
